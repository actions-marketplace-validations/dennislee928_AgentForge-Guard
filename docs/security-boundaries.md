# Security Boundaries

**Prompt instructions are not a security boundary.** Real boundaries are OS sandboxes, filesystem permissions, cloud IAM, Kubernetes RBAC, database roles, scoped tokens, network policy and human approval. `afg` adds a policy layer and execution backends on top of these; it does not replace them.

## Two modes, two levels of assurance

### Managed mode: `afg run -- <argv>`

`afg` itself evaluates the policy and spawns the process:

- argv is structured; there is never an implicit shell.
- The executable is resolved to a canonical absolute path.
- The environment is cleared to an allowlist.
- Approval is read only from the controlling TTY.
- Container runs use a filtered snapshot with no network.
- Every decision is written to the audit log.

This is the only mode in which `afg` **enforces** policy.

### Integration mode: agent hooks and settings

Claude Code hooks and permission rules, and Codex sandbox and approval settings, call the same policy engine. Their strength is bounded by:

- whether the agent routes every action through the hook (some tools, such as file reads and network access, may not go through `Bash`);
- how the agent tokenizes shell strings, since `afg` can only classify what it is shown;
- the agent's own sandbox.

Integration mode is **defense in depth, not enforcement**. It must never be advertised as equivalent to managed mode.

## Remote sandboxes do not protect local secrets automatically

A remote or container sandbox cannot read host secrets **unless they are sent in**. However, an agent running on the host with filesystem access can still read `~/.ssh` and send it elsewhere. You also need:

- Agent-level read deny rules for protected paths (generated by `afg agents sync`, v0.2).
- Manifest-filtered uploads that exclude `.env*`, keys, certificates and git-ignored files.
- Least-privilege credentials and no production credentials on development machines.

## Non-claims

- Allowing `go test` or `cargo test` does not make the tests safe. Test binaries can do anything.
- Matching argv does not prove a command is harmless.
- Docker isolation is only as strong as the Docker runtime and kernel.

## Known limitations (v0.1)

- **Approval via the terminal.** `require-approval` reads `yes` from `/dev/tty`, never from stdin. A process that controls a **pseudo-terminal**, such as an agent that allocates a PTY or `script(1)`, can answer that prompt itself.
- **Out-of-band approval.** When there is no terminal, `afg run` records a pending request and exits 126. A human then runs `afg approve <id>` in their own terminal, which writes a single-use HMAC token. The token is bound to the exact argv, cwd, backend, rule and policy hash, and expires after 15 minutes. An agent can't approve its own request through afg, because:
  - `afg` can never be run through `afg` (a built-in forbidden rule, in both managed mode and the hook);
  - the key directory `~/.config/agentforge` is a protected path.

  An agent that can run arbitrary processes outside afg can still do anything the user can, including running `afg approve`. In that setting, use `deny` for operations that must never come from an agent.
- **Redaction** is pattern-based and best effort. Environment values are never recorded, and command output is stored only as a length and a SHA-256.
- **Container runs work on a copy.** Writes inside the container are discarded. Gitignored and protected files are absent, so a script that needs them fails rather than leaking them.
- **Container images.** Images are referenced by tag and pulled when missing. Pin `image@sha256:…` in production policies.
- **Local T1 commands** (builds and tests) run with the user's privileges and with `HOME` set. A test can read anything the user can read. Route T1 to a container (`policies/strict.yaml`) when that is not acceptable.
- **The audit log** is local and append-only, but not tamper-proof: the user, and any process running as the user, can edit it.
- **Policy pinning depends on afg's environment.** The pin lives under `$HOME/.config/agentforge`. An agent that can launch afg directly, with an environment it chooses (`HOME=/elsewhere afg run …`), sees "not pinned" (a warning) rather than "changed" (a deny). Agents confined to afg or to the hook can't do this, because `HOME=… afg` is both an opaque assignment and a forbidden self-invocation.
- **An external security review has not happened yet.** The T13.2 review was internal: a structured red-team pass over the threat model, with a regression test for each finding. An independent review is a release blocker for v1.0 (see SECURITY.md).
